# AutoSync — Architecture

## Стек

| Слой | Технология | Почему |
|---|---|---|
| Backend API | Python + Flask | основной стек разработчика, быстрый старт REST API |
| LLM | Qwen2.5-14B (локально, Ollama/vLLM) | не зависит от внешних API-ключей, приемлем по цене/скорости для генерации текста и сопоставления |
| БД | PostgreSQL | реляционные данные (товары, заказ-наряды, сопоставления), нужны транзакции |
| Очередь задач | Celery + Redis | плановые job'ы: подтяжка аналитики по расписанию, обработка загруженных документов асинхронно |
| Frontend | React | дашборд для approve/reject предложений по цене и карточкам, загрузка документов |
| Парсинг документов | pandas / openpyxl (Excel), pdfplumber (PDF) | стандартный набор для табличных/PDF данных |
| Деплой | Docker Compose | всё локально разворачиваемо, включая LLM-сервис |

## Внешние интеграции

- **Ozon Seller API / Performance API** — свои товары, продажи, позиции.
- **Сторонний аналитический сервис по Ozon** (MPSTATS / Moneyplace / аналог — уточнить с заказчиком) — данные по конкурентам легально, без прямого скрейпинга.
- **API поставщика запчастей** — цены, наличие, кросс-номера аналогов.

## Потоки данных

**Модуль 1 (Ozon), плановый цикл:**
```
Celery beat (по расписанию)
  → sync_ozon_prices.py
    → ozon_client.py (свои данные)
    → analytics_provider.py (данные по рынку)
  → сохранение в PriceSnapshot
  → llm_client.py анализирует снимок → предложение по цене/карточке
  → фронт: PricingDashboard показывает предложение → человек approve/reject
```

**Модуль 2 (заказ-наряды), по загрузке файлов:**
```
Пользователь загружает договор + заказ-наряд (frontend)
  → API принимает файлы → ставит задачу в очередь
  → process_upload.py:
      document_parser.py парсит оба файла в таблицы
      matcher.py сопоставляет позиции:
        1. точное совпадение артикула
        2. если нет — запрос в parts_supplier_client.py (кросс-номера)
        3. если и там нет — llm_client.py сопоставляет по названию (fallback)
  → результат: PartMatch записи со статусом confidence (exact / cross-ref / llm-guess)
  → фронт: ReviewMatches — человек проверяет позиции с низким confidence
  → генерация итогового документа
```

## Ключевые решения и почему

- **LLM как отдельный сервис (`llm-service/`), а не встроен в backend** — оба модуля обращаются к нему через HTTP, легко заменить модель или вынести на отдельную машину с GPU, не трогая backend.
- **Confidence-статусы в сопоставлении запчастей** — LLM-догадка никогда не должна выглядеть так же надёжно, как точное совпадение по API поставщика. Фронт обязан визуально различать эти статусы.
- **Человек в контуре на изменении цен и на low-confidence сопоставлениях** — до накопления статистики точности автоприменение отключено намеренно.
- **Ozon-скрейпинг исключён архитектурно** — данные по конкурентам идут только через легальный сторонний сервис, чтобы не рисковать баном аккаунта клиента.

## Второй режим развёртывания: native-приложение без Docker

Стек выше (Postgres + Redis + Celery + Docker Compose) — основной, рассчитан
на серверное/масштабируемое развёртывание. Для случая «поставить на одну
машину как обычную программу» (заказчик прямо просил без Docker и без
«танцев с бубном») есть параллельный режим — тот же backend-код, но:

| Слой | Docker-режим | Native-режим |
|---|---|---|
| БД | PostgreSQL | SQLite (файл в `~/.autosync/autosync.db`) |
| Асинхронные задачи | Celery + Redis | `ThreadPoolExecutor` (загрузки) + `APScheduler` (плановый синк цен), см. `app/services/job_queue.py` |
| LLM-сервис | Docker-контейнер | тот же `llm-service/server.py`, поднят в отдельном потоке того же процесса |
| Frontend | nginx-контейнер | этот же Flask отдаёt собранный `frontend/dist` как статику |
| UI | браузер, открывает пользователь | собственное окно (pywebview: WebView2/WebKitGTK), открывает сам процесс |
| Упаковка | `.deb` (постинст сам ставит Docker и поднимает compose) | PyInstaller-бинарник: один exe/ELF, всё вшито |
| Первый администратор | `flask users create-admin` (CLI) | мастер `/setup` в окне приложения при первом запуске |

Переключение — через `app.config.py: Config` vs `NativeConfig` (флаги
`USE_CELERY`, `SERVE_FRONTEND`) и точку входа: `wsgi.py`+`celery_worker.py`
(Docker) против `native_app.py` (native). Бизнес-логика задач (парсинг +
сопоставление, синк цен) вынесена в обычные функции —
`app/services/repair_order_processor.py`, `app/services/price_sync.py` — и
вызывается либо из Celery-задачи, либо напрямую; сам код сопоставления/
парсинга/LLM-вызовов идентичен в обоих режимах.

**Окно вместо браузера (`native_app.py: run_window`)** — единая точка входа
и предсказуемый жизненный цикл: закрытие окна полностью завершает процесс
(включая плановый синк цен через APScheduler), без фонового режима/иконки
в трее. Backend слушает `0.0.0.0`, а не только `127.0.0.1` — пока окно
открыто, AutoSync доступен и по обычному браузеру с телефона/другого ПК в
той же сети, на адресе этой машины. Frontend для native-сборки собирается
с `VITE_API_BASE_URL=/api` (относительный путь, не абсолютный
`http://localhost:PORT`) — иначе запросы из окна (открытого на `127.0.0.1`)
или с LAN-клиента (открытого на IP машины) считались бы кросс-origin и
блокировались бы браузером/webview, т.к. в native-режиме CORS-заголовки
осознанно не выставляются (см. `app/__init__.py`: `SERVE_FRONTEND` ⇒ без
`flask-cors`, предполагая один origin).

**Почему не просто «убрать Docker и оставить Postgres»:** нужно, чтобы один
установочный файл ставился на машину без предварительной установки
СУБД/брокера очереди — SQLite и встроенный планировщик убирают эти
внешние зависимости целиком, ценой худшей горизонтальной масштабируемости
(некритично для одного автосервиса на одной машине).

## Открытые вопросы (не архитектурные решения, а то, что нужно уточнить у заказчика)

- Какой именно сторонний аналитический сервис по Ozon подключаем.
- Точная схема ответа API поставщика запчастей (какие поля доступны для кросс-референсов).
- Порог confidence, ниже которого сопоставление обязательно уходит на ручную проверку.
