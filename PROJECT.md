# AutoSync

## Что это

Внутренняя платформа для автосервиса, который также торгует на Ozon. Состоит из двух независимых, но связанных общей инфраструктурой модулей:

1. **Ozon Module** — аналитика продаж, мониторинг цен конкурентов, автогенерация карточек товаров.
2. **Repair Orders Module** — автоматизация заказ-нарядов: сопоставление запчастей из договора с заказ-нарядом, подбор аналогов через API поставщиков, пересчёт цен.

Оба модуля используют общий локальный LLM-сервис (Qwen2.5) и общую БД, но развёрнуты и масштабируются независимо.

## Зачем

Ручная работа съедает время в двух конкретных местах бизнеса:
- Ценообразование и карточки на Ozon требуют постоянного мониторинга конкурентов — сейчас делается вручную или не делается вовсе.
- Заказ-наряды собираются вручную сверкой договора и текущего прайса — рутина, подверженная ошибкам в артикулах.

## Модуль 1: Ozon — аналитика и карточки

**Вход:** данные по своим товарам (Ozon Seller API), данные по рынку/конкурентам (сторонний аналитический сервис — см. ниже, почему не самописный парсер).

**Что делает:**
- Собирает свои продажи и позиции в выдаче.
- Тянет цены/продажи конкурентов через легальный источник.
- LLM генерирует SEO-тексты, буллеты и характеристики карточек на основе анализа топовых конкурентных карточек.
- Предлагает корректировку цены (не применяет автоматически без подтверждения — см. ограничения).

**Важное архитектурное решение:** мы **не скрейпим Ozon напрямую**. Прямой парсинг чужих карточек нарушает ToS площадки и ведёт к бану аккаунта/IP. Вместо этого: Ozon Seller/Performance API (свои данные, официально) + сторонний аналитический сервис с легальным API (MPSTATS/Moneyplace/аналог, данные по рынку). Это медленнее в поставке фичи, но не рискует аккаунтом клиента.

## Модуль 2: Заказ-наряды

**Вход:** список запчастей из договора (Excel/PDF) + текущий заказ-наряд.

**Что делает:**
- Парсит оба документа в структурированные таблицы.
- Ищет аналоги/кросс-номера через API базы поставщиков (уже есть доступ — не нужен веб-скрейпинг сайтов).
- LLM сопоставляет позиции по названию/артикулу там, где прямого совпадения нет.
- Отдельно сопоставляет строки работ с нормо-часами (`LaborLine`/`LaborCatalogEntry`/AutoData) —
  клиент раньше вписывал часы вручную, теперь это автоматизировано так же, как запчасти.
- Дополняет список работ операциями, которых нет в черновике заказ-наряда, но которые технологически
  идут вместе с уже вписанными (например, сопутствующая мойка/дефектовка узла, который и так
  разбирают) — `labor_matcher.suggest_missing_labor_operations()`. Найдено по реальному тестовому
  файлу заказчика: эталонный результат содержал на 7 работ больше, чем черновик мехника. Как и все
  остальные позиции, предложенные работы попадают в ReviewMatches со статусом «на проверке» и
  пометкой «предложено системой» — automatически в документ не попадают.
- Обогащает каждое сопоставление данными из внутренней номенклатуры/склада заказчика (код, № кат.,
  производитель, остаток, резерв, склад — `NomenclatureEntry`, см. «Ограничения и допущения» ниже
  про источник данных).
- Генерирует итоговый заказ-наряд с подставленными ценами и складскими метаданными.

**Почему через API поставщика, а не "модель гуглит сайты":** артикулы запчастей содержат опечатки и вариации написания, сверка текстом без структурированной базы кросс-номеров даёт много ошибок. API поставщика даёт достоверные кросс-референсы.

## Ограничения и допущения (проверить с заказчиком)

- Автоприменение цен на Ozon — под вопросом: рекомендую человека в контуре (approve/reject) минимум на старте, пока не накоплена статистика точности модели.
- Нужно уточнить, какой именно сторонний аналитический сервис по Ozon использовать (у клиента пока нет предпочтения — см. обсуждение).
  Тот же провайдер должен отдавать не только агрегатные min/avg/max по цене, но и сами топовые
  карточки конкурентов с признаками продаж (`sales_rank`/`units_sold_30d`/`rating`) — это то, что
  реально нужно для «создавай карточку на основе того, что лучше продаётся» из исходной задачи, а не
  просто ценовой срез рынка. Контракт под это уже есть (`AnalyticsProvider.get_top_competitor_listings()`,
  `/v1/competitors/top-listings` — плейсхолдер), но нужно подтвердить, что выбранный провайдер вообще
  отдаёт такие поля по отдельным SKU/карточкам, а не только по категории в среднем.

  Что спросить у заказчика:
  1. Провайдер вообще выбран (MPSTATS/Moneyplace/другой), или ещё нет? Пока не выбран — `AnalyticsProvider`
     не сможет подключиться в принципе (падает с понятной ошибкой, см. `test_connection()`), карточки
     генерируются без анализа конкурентов, а цены — без `competitor_min_price`/`competitor_avg_price`.
  2. Есть ли уже доступ/API-ключ, или это тоже предстоит оформить?
  3. Пример реального ответа API (хотя бы по одному запросу) — нужен, чтобы поправить пути/разбор
     ответа в `get_competitor_prices()`/`get_top_competitor_listings()` под реальную схему.
  4. Подтверждение, что провайдер отдаёт `sales_rank`/`units_sold_30d`/`rating` по конкретным
     карточкам/SKU, а не только агрегаты по категории — без этого «топ карточек по продажам» не
     реализовать, придётся откатиться на чистый ценовой анализ.

- Нужен точный список полей в API поставщика запчастей (что отдаёт: только цену/наличие или ещё кросс-номера аналогов).
  По словам заказчика доступ к этому API уже есть — не хватает только документации/схемы ответа
  (`services/parts_supplier_client.py`, `find_cross_references()` — контракт зафиксирован, реализация
  запроса под реальный API не донастроена).

  Что спросить у заказчика:
  1. Есть ли документация/OpenAPI-схема на API поставщика, или доступ выдан без неё (тогда нужен
     хотя бы пример реального запроса/ответа)?
  2. `find_cross_references()` — отдаёт ли API вообще кросс-номера/аналоги, или только цену и
     наличие по точному артикулу? Если кросс-номеров нет — этот путь сопоставления (`ConfidenceLevel.CROSS_REF`
     в `matcher.py`) не будет работать, и все непрямые совпадения будут уходить сразу на LLM-фоллбек.
  3. Есть ли у API лимиты на частоту запросов (rate limit) — важно, если сопоставление будет идти
     по каждой позиции заказ-наряда отдельным запросом.

- Нормо-часы (`AutoDataClient`/`LaborCatalogEntry`) сейчас работают только по локальному справочнику,
  наполняемому вручную через UI «Нормо-часы» — реального доступа к AutoData (или аналогу) нет.
  Это же ограничение теперь напрямую влияет на новую функцию «система дополняет список работ»
  (`labor_matcher.suggest_missing_labor_operations()`) — предложения по недостающим операциям
  настолько же полны и точны, насколько полон вручную заполненный справочник по конкретной
  марке/модели.

  Что спросить у заказчика:
  1. Есть ли доступ к AutoData (или аналогичной базе нормо-часов), или справочник так и предполагается
     наполнять вручную по мере работы?
  2. Если справочника для марки/модели ещё нет — сколько операций разумно завести заранее (весь
     типовой ремонт, скажем, двигателя, а не только то, что встретилось в первом заказ-наряде) —
     иначе «дополнение списка работ» не сможет ничего предложить сверх того, что мехник и так вписал.
- **Источник таблицы номенклатуры/остатков — открытый вопрос, но заготовка уже реализована.** На
  созвоне (2026-08-07) заказчик пожаловался, что при сборке заказ-наряда вручную сопоставляет
  позиции с внутренней номенклатурой (поля: код, наименование, № кат., производитель, кол-во,
  остаток, заказано, в резерве, в производстве, склад, единица, цена, сумма) — это выглядит как
  выгрузка из 1С/учётной системы самого автосервиса, а не прайс внешнего поставщика. Часы работ
  (вторая часть той же жалобы) уже были автоматизированы — `LaborLine`/`LaborCatalogEntry`/
  `labor_matcher.py` через AutoData, с ручным approve/reject в ReviewMatches.

  Не дожидаясь ответа заказчика, добавлена заготовка по тому же принципу, что и AutoData: модель
  `NomenclatureEntry` (см. `app/models/nomenclature.py`), `services/nomenclature_import.py` —
  загрузка выгрузки файлом (Excel/ODS/CSV, RU-синонимы колонок) через UI «Номенклатура» — и
  `services/nomenclature_client.py`/`nomenclature_matcher.py`, которые обогащают каждый `PartMatch`
  найденной записью (точно по коду, иначе нечётким совпадением по названию — `difflib`, без LLM) и
  выводятся в ReviewMatches/CSV-экспорте/итоговом документе. Если базового URL нет — работает
  полностью локально по загруженной таблице; если заказчик подтвердит реальный API — донастраивается
  `_find_remote()` в `nomenclature_client.py`, как и `analytics_provider.py`/`parts_supplier_client.py`.

  Что всё ещё нужно спросить у заказчика, чтобы не остаться на файловой загрузке навсегда:
  1. В какой системе ведётся номенклатура/остатки (1С — какая конфигурация, отдельная складская
     программа, Excel-таблица вручную)?
  2. Есть ли у этой системы API/веб-сервис (например, 1С OData), к которому можно подключиться, или
     доступна только выгрузка файлом?
  3. Насколько часто меняются остатки — критично ли получать их в реальном времени, или выгрузка
     раз в день/по кнопке приемлема?
  4. Пример реального файла/ответа API с этой таблицей — нужен, чтобы проверить, что эвристика
     распознавания колонок в `nomenclature_import.py` действительно покрывает его формат.

## Для новых разработчиков

Если чините Ozon-модуль — не трогайте `services/ozon_client.py` в сторону прямого HTTP-скрейпинга страниц Ozon, даже "временно для дебага". Если нужны данные, которых нет в Seller/Performance API — это разговор с продактом, не инженерное решение в одиночку.

Если чините Repair Orders — вся логика сопоставления живёт в `services/matcher.py`, LLM вызывается только как fallback, когда прямого совпадения по артикулу нет через API поставщика.
