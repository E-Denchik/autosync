# AutoSync

## Что это

Внутренняя платформа для автосервиса, который также торгует на Ozon. Состоит из двух независимых, но связанных общей инфраструктурой модулей:

1. **Ozon Module** — аналитика продаж, мониторинг цен конкурентов, автогенерация карточек товаров.
2. **Repair Orders Module** — автоматизация заказ-нарядов: сопоставление запчастей из договора с заказ-нарядом, подбор аналогов через API поставщиков, пересчёт цен.

Оба модуля используют общий локальный LLM-сервис (Qwen2.5) и общую БД, но развёрнуты и масштабируются независимо.

## Зачем

Ручная работа съедает время в двух конкретных местах бизнеса:
- Ценообразование и карточки на Ozon требуют постоянного мониторинга конкурентов — сейчас делается вручную или не делается вовсе.
- Заказ-наряды собираются вручную сверкой договора и текущего прайса — рутина, подверженная ошибкам в артикулах.

## Модуль 1: Ozon — аналитика и карточки

**Вход:** данные по своим товарам (Ozon Seller API), данные по рынку/конкурентам (сторонний аналитический сервис — см. ниже, почему не самописный парсер).

**Что делает:**
- Собирает свои продажи и позиции в выдаче.
- Тянет цены/продажи конкурентов через легальный источник.
- LLM генерирует SEO-тексты, буллеты и характеристики карточек на основе анализа топовых конкурентных карточек.
- Предлагает корректировку цены (не применяет автоматически без подтверждения — см. ограничения).

**Важное архитектурное решение:** мы **не скрейпим Ozon напрямую**. Прямой парсинг чужих карточек нарушает ToS площадки и ведёт к бану аккаунта/IP. Вместо этого: Ozon Seller/Performance API (свои данные, официально) + сторонний аналитический сервис с легальным API (MPSTATS/Moneyplace/аналог, данные по рынку). Это медленнее в поставке фичи, но не рискует аккаунтом клиента.

## Модуль 2: Заказ-наряды

**Вход:** заказ-наряд + договор — фиксированный каталог контракта/тендера
(`Contract`/`ContractPart`/`ContractLaborNorm`). Договор загружается **один
раз на весь срок контракта** (`app/api/contracts.py`, «Каталоги контрактов»
в UI) и переиспользуется для всех заказ-нарядов по этому контракту — не
нужно грузить тот же Excel заново на каждый заказ-наряд. Причина: у
госконтрактов/тендеров список разрешённых запчастей и работ фиксирован
(«иные ставить нельзя»), и заводить его в 1С как обычную номенклатуру
означает засорить общий каталог заказчика одноразовым, контракт-специфичным
списком. Каждая сторона (и договор, и заказ-наряд) — один или несколько
файлов (например, отдельные страницы заказ-наряда), в любом из форматов:
Excel/ODS/CSV/Word/PDF, а также сканы/фото (JPG/PNG, или PDF без текстового
слоя) — для них текст сначала распознаётся Tesseract OCR, затем
структурируется в таблицу через LLM (`document_parser.parse_document_with_ocr_fallback`,
`services/ocr.py`). Как и LLM-сопоставление по названию, результат
распознавания скана — самый ненадёжный источник и всегда уходит на ручную
проверку.

Реальные тендерные каталоги легко достигают 50 000+ строк на одну марку
(см. `testdata/Приложение со списком запчастей.xlsx` — суммарно за 200 000
строк по всем маркам). Поэтому каталог контракта хранится не JSON-полем, а
настоящими индексированными таблицами (`ContractPart.article`,
`ContractLaborNorm.operation_name`) с bulk-вставкой при импорте
(`contract_catalog_import.py`) — сопоставление каждой позиции заказ-наряда
идёт индексированным SQL-запросом, а не Python-перебором всего каталога.

**Что делает:**
- Парсит документы в структурированные таблицы.
- Сопоставляет каждую позицию заказ-наряда с каталогом КОНКРЕТНОГО контракта
  (`matcher.match_all_against_contract`): точный артикул → кросс-номера через
  API поставщика → LLM по названию (fallback, на ограниченной выборке
  кандидатов из контракта, не на всём каталоге).
- LLM сопоставляет позиции по названию/артикулу там, где прямого совпадения нет.
  **Подтверждено заказчиком (2026-08-18):** это основной, а не редкий случай —
  «список запчастей уже с падением [ценой после торгов], только вот эти
  запчасти должны использоваться, но мы используем другие — надо, чтобы
  подбирал аналогичные из этого списка с этими ценами». То есть точное
  совпадение артикула — редкость, обычный путь — сопоставление по названию
  с ценой из каталога контракта (не из заказ-наряда).
- Сопоставляет строки работ с нормо-часами — если у контракта есть свой
  фиксированный список работ (`ContractLaborNorm`), матчинг идёт СТРОГО по
  нему, без подмешивания общего справочника `LaborCatalogEntry`/AutoData;
  иначе — по общему справочнику, как раньше. **Подтверждено заказчиком:**
  контракты с фиксированным списком РАБОТ — редкость (на его памяти две
  организации так делают), в 98% случаев справочника нет вообще и норма
  часов/затраченное время просто вписываются вручную по факту — список работ
  в этом случае и должен браться из самого черновика заказ-наряда (уже
  реализовано, `_parse_repair_order_files`), а не из контракта.
- Цена нормо-часа может быть своя на каждую марку ТС в рамках одного контракта
  (`ContractHourlyRate`, вкладка «Ставки по маркам» в каталоге контракта) —
  подтверждено заказчиком: «цену норма часа он подтягивает из контракта, это
  тоже отдельным файлом, там на каждую марку своя норма часа». Формат этого
  отдельного файла заказчик пока не присылал — сейчас ставки заводятся
  вручную через UI; при получении реального файла нужно добавить его в
  `contract_catalog_import.py`. Если для марки заказ-наряда своей ставки в
  контракте нет — используется ставка контрагента (`Contragent.hourly_rate`),
  как раньше.
- Каталог контракта живёт весь срок контракта (у заказчика — от полугода до
  года, суммы контрактов до ~2 млн ₽), после чего заказчик выигрывает новый
  тендер (обычно с другой скидкой/«падением») и полностью заменяет список.
  Поэтому вместо удаления — архивация (`Contract.active`, кнопка
  «Архивировать» в UI): скрывает контракт из списка выбора для новых
  заказ-нарядов, но не ломает историю уже созданных (жёсткое удаление
  по-прежнему заблокировано, пока есть привязанные заказ-наряды).
- Дополняет список работ операциями, которых нет в черновике заказ-наряда, но которые технологически
  идут вместе с уже вписанными (например, сопутствующая мойка/дефектовка узла, который и так
  разбирают) — `labor_matcher.suggest_missing_labor_operations()`. Найдено по реальному тестовому
  файлу заказчика: эталонный результат содержал на 7 работ больше, чем черновик мехника. Как и все
  остальные позиции, предложенные работы попадают в ReviewMatches со статусом «на проверке» и
  пометкой «предложено системой» — automatически в документ не попадают.
- Обогащает каждое сопоставление данными из внутренней номенклатуры/склада заказчика (код, № кат.,
  производитель, остаток, резерв, склад — `NomenclatureEntry`, см. «Ограничения и допущения» ниже
  про источник данных).
- Генерирует итоговый заказ-наряд с подставленными ценами и складскими метаданными.

**Почему через API поставщика, а не "модель гуглит сайты":** артикулы запчастей содержат опечатки и вариации написания, сверка текстом без структурированной базы кросс-номеров даёт много ошибок. API поставщика даёт достоверные кросс-референсы.

## Ограничения и допущения (проверить с заказчиком)

- Автоприменение цен на Ozon — под вопросом: рекомендую человека в контуре (approve/reject) минимум на старте, пока не накоплена статистика точности модели.
- Нужно уточнить, какой именно сторонний аналитический сервис по Ozon использовать (у клиента пока нет предпочтения — см. обсуждение).
  Тот же провайдер должен отдавать не только агрегатные min/avg/max по цене, но и сами топовые
  карточки конкурентов с признаками продаж (`sales_rank`/`units_sold_30d`/`rating`) — это то, что
  реально нужно для «создавай карточку на основе того, что лучше продаётся» из исходной задачи, а не
  просто ценовой срез рынка. Контракт под это уже есть (`AnalyticsProvider.get_top_competitor_listings()`,
  `/v1/competitors/top-listings` — плейсхолдер), но нужно подтвердить, что выбранный провайдер вообще
  отдаёт такие поля по отдельным SKU/карточкам, а не только по категории в среднем.

  Что спросить у заказчика:
  1. Провайдер вообще выбран (MPSTATS/Moneyplace/другой), или ещё нет? Пока не выбран — `AnalyticsProvider`
     не сможет подключиться в принципе (падает с понятной ошибкой, см. `test_connection()`), карточки
     генерируются без анализа конкурентов, а цены — без `competitor_min_price`/`competitor_avg_price`.
  2. Есть ли уже доступ/API-ключ, или это тоже предстоит оформить?
  3. Пример реального ответа API (хотя бы по одному запросу) — нужен, чтобы поправить пути/разбор
     ответа в `get_competitor_prices()`/`get_top_competitor_listings()` под реальную схему.
  4. Подтверждение, что провайдер отдаёт `sales_rank`/`units_sold_30d`/`rating` по конкретным
     карточкам/SKU, а не только агрегаты по категории — без этого «топ карточек по продажам» не
     реализовать, придётся откатиться на чистый ценовой анализ.

- **Поставщики запчастей подключены и подтверждены (2026-08-21):** вместо изначально задуманного
  единого API поставщика заказчик работает с тремя разными — Rossco (`services/rossco_client.py`,
  SOAP), АвтоЕвро (`services/autoeuro_client.py`, REST) и Москворечье (`services/moskvorechye_client.py`,
  протокол ABCP). Все три подключены и проверены реальными ключами заказчика (Администрирование →
  Интеграции). `find_cross_references()` у каждого клиента отдаёт кросс-номера аналогов, а не только
  цену/наличие по точному артикулу — путь `ConfidenceLevel.CROSS_REF` в `matcher.py` реально работает.

  `services/parts_supplier_client.py: AggregatedPartsSupplierClient` опрашивает все настроенные
  поставщики параллельно и объединяет результат в один список кросс-номеров, поэтому `matcher.py`
  по-прежнему видит один объект с одним методом `find_cross_references(article)`; отказ одного
  поставщика (сеть, протухшие ключи, лимит) не останавливает сопоставление — остальные поставщики
  и LLM-фоллбек всё равно отрабатывают. `services/supplier_search.py` — отдельный путь для ручного
  подбора оператором (карточка ошибки на каждого поставщика отдельно, см. `SupplierSearchModal.jsx`),
  использует те же три клиента напрямую, без агрегации.

  Изначально задуманный единый `PARTS_SUPPLIER_BASE_URL`/`PARTS_SUPPLIER_API_KEY` (generic
  `PartsSupplierClient` в том же файле) остаётся в коде как опциональный четвёртый источник — схема
  его ответа заказчиком так и не была подтверждена, используется только если ключи заданы явно.

- **Источник номенклатуры/остатков и нормо-часов подтверждён (2026-08-16):** реальная система
  заказчика — 1С:Предприятие 8, конфигурация «Альфа-Авто: Автосалон+Автосервис+Автозапчасти ПРОФ»,
  ред. 5.1 (подтверждено по скриншотам живой базы). Один и тот же сервер отдаёт и номенклатуру/остатки
  (заказ-наряд → вкладка «Товары»: код, наименование, остаток, заказано, в резерве, в производстве,
  склад, цена), и нормо-часы (вкладка «Работы»: норма часов, цена н/ч) — поэтому `AutoDataClient` и
  `NomenclatureClient` теперь используют одно общее подключение (`ALFAAUTO_BASE_URL`/`ALFAAUTO_LOGIN`/
  `ALFAAUTO_PASSWORD`, см. «Интеграции» в UI).

  Реалистичный способ подключения к 1С — встроенный протокол OData (HTTP Basic Auth логином/паролем
  пользователя 1С, у 1С нет единого bearer-токена), доступен без написания кода в самой 1С, если
  администратор включит веб-публикацию базы с галочкой OData. `discover_entities()` в обоих клиентах
  дергает стандартный корневой OData-документ (одинаковый для любой конфигурации 1С) и возвращает
  список реально опубликованных объектов — так можно узнать точные имена без угадывания.

  Что ещё не подтверждено вживую (нет доступа к реальному серверу):
  1. Опубликована ли у заказчика веб-публикация с OData вообще (сейчас видели только доступ через
     толстый клиент по RDP) — нужно узнать у его 1С-администратора/интегратора.
  2. Реальные имена объектов OData для этой конфигурации (`_find_remote()` в `nomenclature_client.py`
     и `find_norm_hours()` в `autodata_client.py` сейчас обращаются к `Catalog_Номенклатура`/
     `Catalog_НормыВремени` — это предположение по стандартным именам 1С, не проверено вживую; после
     `discover_entities()` на реальной базе нужно донастроить под то, что там реально называется).
  3. Насколько часто меняются остатки — критично ли реальное время, или периодический опрос достаточен.

- **Новая, отдельная интеграция — MotorData** (запрошено заказчиком 2026-08-18, доступа пока нет —
  ждёт лицензию, собирается созвониться с MotorData по этому поводу). Это не про 1С выше — про
  случай, когда у контракта НЕТ фиксированного списка работ (98% случаев, см. «Что делает» модуля 2):
  сейчас мехник просто вписывает норма-часы из головы, и заказчик хочет вместо этого, чтобы система
  по названию операции из заказ-наряда (например, «замена шаровой») обращалась в MotorData, получала
  оттуда норму часов и весь набор сопутствующих операций, которые физически нужны для её выполнения
  (например, «снять колёса»). Похоже на уже готовый `labor_matcher.suggest_missing_labor_operations()`
  по форме (предложить недостающие операции), но с MotorData как источником кандидатов вместо
  локального `LaborCatalogEntry`/1С — реализовывать саму интеграцию рано, пока нет реального доступа
  и документации API (тот же принцип, что и с остальными внешними API в этом разделе — не гадать
  на структуре ответа без реальных данных).

  Что спросить у заказчика, когда будет доступ:
  1. Реальный пример ответа API MotorData на запрос по операции/марке-модели — конкретные поля,
     единицы измерения норма-часов.
  2. Привязка по IP или по ключу — заказчик предполагал, что по IP, нужно подтвердить.

  Пока нет реального доступа, оба клиента работают полностью локально — по таблицам
  `NomenclatureEntry`/`LaborCatalogEntry`, наполняемым загрузкой файла или вручную через UI.

## Для новых разработчиков

Если чините Ozon-модуль — не трогайте `services/ozon_client.py` в сторону прямого HTTP-скрейпинга страниц Ozon, даже "временно для дебага". Если нужны данные, которых нет в Seller/Performance API — это разговор с продактом, не инженерное решение в одиночку.

Если чините Repair Orders — вся логика сопоставления живёт в `services/matcher.py`, LLM вызывается только как fallback, когда прямого совпадения по артикулу нет через API поставщика.
