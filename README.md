# AutoSync

[![Build native packages](https://github.com/E-Denchik/autosync/actions/workflows/build-native.yml/badge.svg)](https://github.com/E-Denchik/autosync/actions/workflows/build-native.yml)

**AutoSync** — внутренняя desktop-платформа для автосервиса, который также
торгует на Ozon. Закрывает два конкретных источника ручной рутины в
бизнесе: мониторинг цен конкурентов и генерацию карточек на Ozon, и
сверку заказ-нарядов с прайс-листами поставщиков при ремонте.

Без Docker, без браузерного доступа и без входа с паролем: один
установочный файл, собственное окно, работает на одной машине заказчика.
Подробности про бизнес-логику — в [PROJECT.md](PROJECT.md), про стек и
устройство кода — в [ARCHITECTURE.md](ARCHITECTURE.md). Этот файл —
практическое руководство: что это, как запустить и как разрабатывать.

## Возможности

**Модуль Ozon** — аналитика продаж и автогенерация карточек:
- Синхронизация каталога товаров, цен и продаж с Ozon Seller API — вручную
  кнопкой или по расписанию раз в 6 часов.
- LLM предлагает корректировку цены с учётом маржи и данных конкурентов —
  автоприменения нет, каждое изменение проходит approve/reject человеком в
  PricingDashboard, и только после этого реально уходит в Ozon.
- LLM генерирует SEO-тексты, буллеты и характеристики карточек на основе
  анализа топовых конкурентных позиций.
- Конкурентные данные — только через легальный сторонний аналитический
  сервис, без прямого скрейпинга страниц Ozon (риск бана аккаунта).

**Модуль заказ-нарядов** — автоматизация сверки ремонта с прайс-листом:
- Приём документов в любом виде: Excel/ODS/CSV/Word/PDF, а также
  сканы и фото (JPG/PNG, PDF без текстового слоя) — через Tesseract OCR
  и LLM-структурирование.
- Каталог контракта/тендера (запчасти + нормо-часы) загружается один раз
  на весь срок контракта и переиспользуется для всех заказ-нарядов по
  нему — тендерные каталоги достигают 50 000+ строк, хранятся в
  индексированных таблицах, а не JSON-полем.
- Трёхуровневое сопоставление позиций: точный артикул → кросс-номера
  через API поставщиков запчастей → LLM по названию как последний fallback,
  с понятной пометкой надёжности каждого статуса.
- Сопоставление строк работ с нормо-часами: по фиксированному списку
  контракта, если он есть, иначе по общему справочнику или по значению,
  указанному прямо в заказ-наряде.
- Массовые approve/reject, ручная пересвязка с поиском по каталогу
  договора, добавление позиций вручную, CSV-экспорт, полный аудит-лог
  изменений.
- Генерация итогового документа — либо встроенным форматом, либо по
  Excel-шаблону заказчика с плейсхолдерами (`{{поле}}`).

Общие для обоих модулей: локальный LLM-сервис (не завязан на облачные
API-ключи), единая база, полный аудит-лог (SCD2) по всем изменяемым
сущностям.

## Технологический стек

| Слой | Технология | Почему |
|---|---|---|
| Backend API | Python + Flask | быстрый старт REST API |
| LLM | Qwen2.5 (локально, Ollama/LM Studio) | не зависит от внешних API-ключей, приемлем по цене/скорости |
| БД | SQLite | файл в каталоге данных пользователя, без отдельного сервера БД |
| Асинхронные задачи | `ThreadPoolExecutor` + `APScheduler` | всё выполняется в одном процессе, без брокера очереди |
| Frontend | React (Vite) | UI-слой; собирается в статику и рендерится **внутри нативного окна** (pywebview), никакого браузера или отдельного веб-сервера — см. ниже |
| Парсинг документов | pandas / openpyxl / python-docx / pdfplumber | Excel/ODS/CSV/Word/PDF без ручной конвертации |
| Распознавание сканов | Tesseract OCR + LLM-структурирование | сканы/фото документов вместо табличного файла |
| Деплой | PyInstaller + pywebview | один exe/ELF, собственное окно, без Docker и браузера |

React здесь — не «браузерное приложение с бэкендом», а UI-слой того же
самого нативного процесса: `npm run build` собирает `frontend/dist`
(статические HTML/JS/CSS), `native_app.py` открывает системное окно
(WebView2 на Windows, WebKitGTK на Linux — не Chromium и не браузер
пользователя) и тот же Flask-процесс отдаёт эту статику прямо в него.
Обычный браузер ОС в этом никак не участвует — ни для UI, ни для API,
подробнее в разделе [«Доступ»](#доступ) ниже.

Подробная структура папок и потоки данных — в
[ARCHITECTURE.md](ARCHITECTURE.md).

## Внешние интеграции

| Интеграция | Протокол | Статус |
|---|---|---|
| Ozon Seller API / Performance API | REST | подключено |
| Rossco — цены/наличие/кросс-номера запчастей | SOAP | подключено, ключи заказчика |
| АвтоЕвро — цены/наличие/кросс-номера запчастей | REST | подключено, ключи заказчика |
| Москворечье — цены/наличие/кросс-номера запчастей | ABCP | подключено, ключи заказчика |
| 1С:Альфа-Авто — номенклатура/остатки и нормо-часы | OData (HTTP Basic Auth) | клиенты готовы, ждём боевой доступ к серверу заказчика |
| Сторонний аналитический сервис по Ozon (конкуренты) | REST | контракт и проверка подключения готовы, провайдер не выбран |

Ключи и статус подключения каждой интеграции — в UI, «Администрирование →
Интеграции». Три поставщика запчастей опрашиваются параллельно и
объединяются в один список кросс-номеров для автосопоставления; для
ручного подбора оператором те же клиенты доступны напрямую через поиск по
поставщикам.

## Скачать готовую сборку

Собирается автоматически в CI (`.github/workflows/build-native.yml`) и
публикуется в [GitHub Releases](../../releases):

- **[Latest build](../../releases/tag/latest)** — пересобирается на каждый
  push в `main`, самая свежая версия, без гарантий стабильности.
- **Версионные релизы** (`vX.Y.Z`) — стабильные, публикуются по тегу.

Скачайте `autosync-desktop_<версия>_amd64.deb` (Linux) или
`autosync-setup-<версия>.exe` (Windows) из нужного релиза — оба
устанавливаются как обычное приложение, см. ниже.

## Установка

**Linux**

```bash
sudo apt install ./autosync-desktop_<версия>_amd64.deb
```
Именно `apt install`, а не `dpkg -i` — так системные зависимости (окно,
Tesseract OCR) подтянутся сами. Дальше — запуск из меню приложений
(«AutoSync») либо `/opt/autosync/autosync`.

**Windows**

Скачать `autosync-setup-<версия>.exe`, запустить, пройти обычный мастер
установки (права администратора не нужны — ставится в профиль пользователя).
Ничего доустанавливать не нужно.

`.exe` не подписан цифровой подписью (платный код-signing сертификат пока
не куплен) — при первом запуске Windows SmartScreen покажет «Windows
защитила ваш компьютер». Это ожидаемо: нажмите **«Подробнее» → «Выполнить
в любом случае»**.

**Требования:** локально установленный [Ollama](https://ollama.com) (или
LM Studio) — нужен только для LLM-функций (предложения по цене, LLM-fallback
сопоставления, генерация карточек, распознавание сканов); всё остальное
работает и без него.

Всё остальное клиент не ставит отдельно — оба пакета самодостаточны:
- Окно приложения: на Linux `.deb` сам подтянет системные пакеты
  (`python3-gi`, `gir1.2-gtk-3.0`, `gir1.2-webkit2-4.1`/`-4.0`) через
  `apt install`; на Windows рантайм WebView2 идёт в составе Windows 10
  (21H2+)/11.
- Tesseract OCR (загрузка сканов/фото документов вместо файла таблицы,
  с русским языковым пакетом): на Linux — тоже зависимость `.deb`,
  `apt install` поставит сам; на Windows бинарник и языковые данные
  запакованы прямо внутри `autosync-setup-<версия>.exe` (см.
  `scripts/build-native-windows.ps1`) — устанавливать Tesseract отдельно
  не нужно.

## Быстрый запуск на Linux из исходников (без установки .deb)

```bash
./scripts/run-native.sh   # соберёт бинарник при первом запуске, дальше просто откроет окно
```

## Сборка пакетов из исходников

```bash
./scripts/build-native-linux.sh   # -> dist/native-linux/autosync (сам бинарник)
./scripts/build-native-deb.sh     # -> dist/autosync-desktop_<версия>_amd64.deb

# Windows — обязательно запускать НА Windows, PyInstaller не кросс-компилирует:
.\scripts\build-native-windows.ps1        # -> dist\native-windows\autosync.exe
# затем Inno Setup по packaging\native-windows\autosync.iss -> установщик .exe
```

Оба .exe/.deb автоматически собираются в CI на реальных Linux- и
Windows-раннерах: `.github/workflows/build-native.yml` — на каждый push в
`main` обновляет pre-release `latest`, на тег `vX.Y.Z` публикует версионный
GitHub Release (см. «Скачать готовую сборку» выше). Сборка запускается
только после того, как backend- и frontend-тесты прошли зелёными — см.
«Тесты и CI» ниже.

## Ключи интеграций (Ozon, поставщики и т.п.)

Ключи внешних API (Ozon Seller/Performance, Rossco/АвтоЕвро/Москворечье и
т.д.) задаются только через UI — страница Администрирование → Интеграции,
сохраняются в базе данных заказчика (см. `app/services/settings_store.py`).

Сборка НЕ вшивает никакие ключи из GitHub Secrets в бинарник: публичный
релиз (.deb/.exe) один и тот же для всех и не содержит секретов ни одного
заказчика — это исключает риск, что чужие ключи утекут вместе с публично
доступным файлом сборки.

## Доступ

Публичных API-эндпоинтов, регистрации или входа с паролем нет — все разделы
приложения доступны сразу, без учётных записей. Backend отвечает только на
запросы из собственного окна приложения (`/api/health` — исключение,
используется для проверки, что процесс жив); из обычного браузера или с
другого устройства в сети AutoSync недоступен. Закрытие окна полностью
завершает приложение, включая плановые задачи — без фонового режима.

## Локальная разработка

**Backend**

```bash
cd backend
python3 -m venv .venv && source .venv/bin/activate
pip install -r requirements-dev.txt

export FLASK_APP=wsgi.py
flask db upgrade

python native_app.py   # откроет своё окно само; БД и загрузки — в data/ (в корне проекта)
```

Запуск из исходников (`python native_app.py`) — это НЕ упакованная сборка,
поэтому Tesseract туда не встроен (см. `native_app.py: configure_tesseract()`
— встраивание срабатывает только для frozen-бинарника). Для разработки OCR
локально доставьте системный `tesseract-ocr`/`tesseract-ocr-rus` сами.

**Frontend**

```bash
cd frontend
npm install
VITE_API_BASE_URL=/api npm run build   # относительный путь — тот же процесс отдаёт и API, и статику
```

Frontend не запускается отдельным dev-сервером (`npm run dev`) в обычном
режиме работы — `native_app.py` отдаёт уже собранный `frontend/dist`
напрямую, тем же процессом, что и API, без браузерного доступа. Для
итеративной разработки UI собирайте `npm run build` после каждого
изменения и перезапускайте `python native_app.py`.

**LLM-сервис** (в обычном режиме поднимается автоматически внутри `native_app.py`)

```bash
cd llm-service
pip install -r requirements.txt
export OLLAMA_BASE_URL=http://localhost:11434
python server.py
```

Требует локально запущенный Ollama (или LM Studio) — конкретную модель
выбирает администратор в UI (Администрирование → LLM-модель).

**Тестирование синхронизации с Ozon без реального кабинета продавца**

У Ozon нет публичной песочницы, поэтому для проверки каталога/категорий/поиска
без реальных ключей есть локальный мок Seller API (`scripts/mock_ozon_api.py`,
8 тестовых товаров в 3 категориях):

```bash
python scripts/mock_ozon_api.py   # слушает 127.0.0.1:5900

# в другом терминале — направляем AutoSync на мок вместо реального Ozon:
export OZON_SELLER_API_BASE=http://127.0.0.1:5900
export OZON_CLIENT_ID=test
export OZON_API_KEY=test
python backend/native_app.py
```

Дальше в UI: Карточки → «Синхронизировать с Ozon» — товары, категории и поиск
заработают на тестовых данных. С реальными ключами `OZON_SELLER_API_BASE` не
задавайте — тогда клиент по умолчанию идёт на настоящий `api-seller.ozon.ru`.

## Тесты и CI

```bash
# backend
cd backend && source .venv/bin/activate && python -m pytest tests/ -q

# frontend
cd frontend && npm run test
```

CI (`.github/workflows/build-native.yml`) прогоняет оба набора тестов
(`test-backend`, `test-frontend`) на каждый push и явно блокирует сборку
бинарников, если хоть один тест красный — публикация `latest`-релиза (а
значит и автообновление на машине заказчика) невозможна без зелёных
тестов между пушем в `main` и выходом сборки.

## Текущий статус

Оба модуля работают целиком, не заглушки:

- **Ozon** — синхронизация каталога, ручное/плановое обновление цен и
  продаж, LLM-предложения по цене и карточкам с approve/reject, реальное
  применение цен в Ozon после подтверждения.
- **Заказ-наряды** — приём документов любого формата (включая сканы),
  переиспользуемые каталоги контрактов, трёхуровневое сопоставление
  запчастей и работ, три реальных поставщика запчастей и 1С:Альфа-Авто,
  массовая проверка, генерация итогового документа по встроенному или
  клиентскому шаблону, полный аудит-лог.

Что осознанно оставлено открытым до уточнения с заказчиком (конфигурация
и проверка подключения для обоих уже готовы в UI — не хватает только
самого провайдера/боевого доступа):

- **Сторонний аналитический сервис по Ozon** (`analytics_provider.py`) —
  конкретный провайдер (MPSTATS/Moneyplace/аналог) ещё не выбран.
- **`MATCH_CONFIDENCE_THRESHOLD`** (0.75 по умолчанию) — порог, ниже
  которого сопоставление обязательно уходит на ручную проверку, нужно
  подтвердить с заказчиком.
- **1С:Альфа-Авто** — клиенты готовы и используют стандартный протокол
  OData, но ещё не проверены на боевом сервере заказчика (нет доступа).
- **MotorData** — запрошенная заказчиком интеграция для подбора нормо-часов
  по названию операции, когда у контракта нет своего списка работ; ждёт
  лицензии и документации API.

Подробности и открытые вопросы к заказчику по каждому пункту — в
[PROJECT.md](PROJECT.md), раздел «Ограничения и допущения».

Ozon-скрейпинг исключён архитектурно — не добавляйте его в `ozon_client.py`
(см. PROJECT.md, «Для новых разработчиков»).
